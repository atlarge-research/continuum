## Agreed merge scope

Ship a complete modular core, a small set of working modules and a clean cut to the new implementation. QEMU is the sole infrastructure module for the merge. The selected software and benchmark modules serve current users and the agreed research and teaching cases. This scope and the packet sequence below supersede the October scope and sequence. ## Implementation packets

Assign one packet at a time per owner. Dependencies name the outputs needed for integration and verification. Source recovery, fixture work and offline analysis can start while those outputs are being prepared. The assignee names the exact edit paths and checks in a short brief, gets an independent plan review, then hands back the diff, check results and any run evidence for independent review. The linked domain plans and case manifest carry the detailed settings. [Repository workflow](../AGENTS.md) · [Case manifest](reproduction_inventory.md#br23-projects-and-case-manifest)

Start with SCOPE and independent artifact and fixture preparation. Integrate the first working slice before expanding live verification. The maintainer can review the implementation together at the end. Bring forward only decisions that need maintainer input, including the exact removal list before the cut, material changes to the agreed scope, and separately authorized release actions. [Approval boundaries](rework_milestone_release_plan.md#2-approved-consolidated-policies)

The first integration slice is QEMU → Kubernetes → image classification. One integrator coordinates the CLI and directory cutover, and packet owners move the files they own with that integrator. Intermediate work can be staged together. The release tree has one CLI and one supported config and execution path. Keep pilot evidence separate from the frozen candidate.
