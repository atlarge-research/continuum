# Continuum Pre-Main Stabilization Policy

## 1. Authority and execution order

The [Continuum rework plan](rework_kickoff.md) sets the agreed release scope, execution sequence and handoffs. This document sets safety, evidence and approval rules. The November scope and sequence supersede the October ones. The October 27 policy and normal-user migration amendment remain available through `git show 7ad43edff8c863c8b610ef5c4d6e2029990c1306:docs/rework_milestone_release_plan.md`. Factual rows and their evidence remain in `docs/release_certification_matrix.md`.

Follow the [packet dependencies](rework_kickoff.md#implementation-packets). Each nontrivial packet needs a bounded exact-file plan, independent read-only plan review, proportional tests, full independent uncommitted diff review, and resolution of actionable findings before a local commit. Routine packet review is handled by agents. Record evidence against the source and workflow that produced it.

## 2. Approved consolidated policies

1. **Required reproductions.** The [selected case manifest](reproduction_inventory.md#br23-projects-and-case-manifest) defines the evidence for the agreed scope. Track full old-main parity for historical disposition and provenance.
2. **Product boundary.** Complete the core cutover, retained modules and selected projects in the [agreed scope](rework_kickoff.md#agreed-merge-scope). Bring material scope changes to the maintainer with the evidence and a proposed resolution.
3. **Stop/resume v1.** Use QEMU with the same revision, base path, topology and software contract. The target phases run infrastructure → software → benchmark. The operator verifies the revision before resume. Cross-commit resume, arbitrary software replacement on mutated VMs and concurrent runs sharing a base path remain unsupported. Allow one active Continuum invocation per Unix account per physical host, even across base paths. Fresh QEMU infrastructure startup stops the account's verified old Continuum guests on the controller and participating workers before provisioning. Resume uses its retained deployment.
4. **Application sweeps.** Sequential same-application runs with changed benchmark parameters remain candidate-only until actual cleanup and idempotence evidence proves safe reuse. This does not authorize unsupported multi-stage benchmark pipelines.
5. **Cache and ownership.** Keep one mutable current QEMU cache per stable runner/host/profile-tokenized owner slot. Runtime runs as the normal user (`matthijs` on the approved node4/node3 hosts), never as root. Sharing one cache between Unix users is unsupported. The approved one-time migration preserves compact evidence and numeric metadata before bounded conversion; it is not runtime permission repair. Remove old accounts and installed wrappers only after replacement runtime verification and an exact UID/ACL retirement audit. For a valid peer, preserve QCOW2/cloud-init identity, owner/group/mode/ACL; coordinated reprovisioning may change disk contents and invalidate/republish only the ready marker. An invalid owner's exact sidecar, QCOW2 and derived cloud-init disk may be removed, never current-run YAML or unrelated peers. Access/cleanup failures must identify the path, operation and operator remedy, with no privilege escalation or automatic ownership repair.
6. **Configuration structure.** Keep experiment, environment profile and software profile as three composed YAML documents. Follow the agreed module-owned configuration contract in the [configuration design](configuration_restructuring_design.md#71-br23-configuration-and-module-cutover). A new validation dependency needs strong evidence that it materially improves the implementation.
7. **Shipped inventory.** Every tracked `.yaml` under `configs/experiments/` and `configs/profiles/` is shipped inventory, including templates with an explicit template classification. Parser acceptance is not runtime support. Inventory legacy `.cfg` inputs and test-only fixtures separately. Each tracked file needs one classification/disposition and zero unaccounted rows before the configuration gate closes.
8. **Registry terminology.** The implemented approved hard cut is `run.registry_refresh: missing|all`, default `missing`, without aliases. Missing refreshes missing/invalid required registry images; all refreshes every required image. Parser, schema, runtime accessors, examples, tests and active docs change together; the removed image_prefetch key is rejected. Cache priming and guest preload are separate operations, not synonyms for this setting. Historical evidence is not migrated or renewed by the cutover.
9. **Retained inspection.** Permanently keep ordinary logs, raw stdout/stderr, metadata, state/lock, benchmark/network artifacts, storage/pruning controls, `latest-result-summary`, and narrowly indexed/full `latest-result-tail`. The temporary diagnostic replay surface is removed after completed diagnosis and exact multi-host verification. Its dedicated playbook/tests are removed; do not replace it with a generalized command runner.
10. **Evidence checks.** Provisionally preserve current checkers. In the slimming review, retain only mechanisms preventing a demonstrated false claim; consolidate proven duplication atomically with audit gates, tests, skills and docs. The current audit script, not an old skill summary, defines required gates. Historical evidence remains truthful and distinct from current runner commands; source freshness checks remain enforced.
11. **Acceptance evidence.** Require the canonical offline audit with complete Python suite coverage, applicable lint, documentation paths and release claims/matrix. Consolidate Python discovery through the testing packet. Require both complete physical operational passes and every other selected release gate on the exact frozen candidate. [Testing design](operational_testing_strategy.md#agreed-testing-changes) · [Acceptance evidence](#5-exact-candidate-acceptance)
12. **Publication and merge.** Obtain separate explicit approval for external actions. Approved workload image uploads may happen once image sources are ready, with digest and cold-pull proof due before merge. Branch publication, merge, tag and release require the final acceptance package and explicit approval. A namespace choice or local packet review gives no publication authority.
13. **Deletion.** Complete the candidate inventory and get approval of the exact paths before reproduction-driven removal. Use bounded, independently reviewed packets and preserve required provenance and evidence. Keep tests that protect supported behavior. Branch deletion requires separate maintainer approval.
14. **Document authority.** The kickoff owns the implementation plan, this document owns release rules, and the plan stack maps the supporting documents. Domain docs describe contracts, the certification matrix records factual row status, and the release handoff preserves dated operational evidence. Earlier phase plans and roadmaps are historical.

## 3. Core versus modules

The core owns validation, composition, selector/scope resolution, module contracts, deterministic planning/runtime handoff, state/lock and evidence contracts. Infrastructure, software and benchmark procedures are modules. QEMU is the retained provider module. Applications supply workload assets, and projects use the CLI and saved results.

Runtime claims require VM-backed or cloud-backed evidence (or host-backed evidence where the particular gate permits it). Static/parser checks cannot certify runtime. Intermediate rework milestones may certify bounded module sets but are not final main replacement releases.

## 4. Factual certification labels

| Label | Meaning |
| --- | --- |
| `core-ready` | Static, unit, parser/repository and runner-contract evidence only. |
| `certified` | The exact row has the evidence required by its matrix gate; candidate freshness is checked separately. |
| `certified-candidate` | Passed previously; needs a fresh candidate run. |
| `ported-unverified` | Code/config exists without current full runtime evidence. |
| `historical` | Preserved legacy input, not a runtime support claim or final scope decision. |
| `deprecated-proposed` | Proposed demotion/removal, requiring scope approval and rationale. |

Do not change row statuses merely because policy or runner identity changed. Historical old-main config rows and `docs/old_main_parity_issue_seed.md` remain a complete transitional candidate inventory until the bounded scope review. Existing local `origin/main` inventory checking stays in place to prevent unaccounted legacy files, not to require every historical feature before main.

## 5. Exact-candidate acceptance

Freeze one clean locally committed candidate after the packets and independent reviews are complete. Record HEAD, empty status, `git diff main...HEAD --stat` and shortstat. Before each physical-host run, record source revision/status and verify the normal-user host prerequisites. Use the live checkout.

Run both complete physical `operational_regression` passes on the frozen commit before the other live gates. Each pass creates four new JSONs with six successful executions, covering three single-entry smoke results and one three-entry benchmark result. Require zero exit codes, no timeouts, no failed or unreachable Ansible hosts, and verified expected teardown. Inspect the actual child results for `infra_one_vm`, `software_k8s_two_vm`, `network_netperf_two_vm` and `benchmark_k8s_resume`.

Run the selected seven-VM serverless configuration after fresh workflows that share its host accounts. Use the qualified OpenFaaS case or the separately identified Knative fallback with the same placement, workload and retention checks. Require the current run YAML and correct QCOW2 access without broad permission repair. Use the exact selected manifest for the remaining research, platform, monitoring and teaching cases. [Serverless qualification and fallback](reproduction_inventory.md#openfaas-qualification-for-br23) · [Case manifest](reproduction_inventory.md#br23-projects-and-case-manifest)

Inspect every JSON and result index for complete stdout/stderr, metadata, state/lock, benchmark/network artifacts, placement and limitations as applicable. Present the final branch delta, reproduction and configuration inventories with zero unaccounted rows, supported boundaries and known limits, commands and results, artifact and image receipts, and independent final review. Recheck the public documentation, projects and post-merge dispositions before requesting explicit merge approval. If the candidate changes, repeat both operational passes and all other gates that require exact-source evidence. [Final handoff](rework_kickoff.md#integration-and-release)
