# Python style and review

When adding or modifying Python code, use the repository's existing Black and Pylint tooling before presenting the work for review. This applies to source files, scripts and tests. Reading files, running existing code/tests, or editing documentation alone does not require reformatting Python.

- Use the Black and Pylint versions listed in `requirements.txt`. Avoid changing tool versions or introducing another formatter as part of unrelated work.
- Run Black on the Python files changed by the task, using `--line-length 100` to match `sysconfig/pylintrc`. Then run Pylint on those files with `--rcfile=sysconfig/pylintrc`, from the repository root and in an environment with the required imports available.
- Fix clear defects and straightforward cleanup findings. Evaluate function/module length, argument count and complexity warnings in context. Prefer focused, readable functions, but do not split coherent code solely to satisfy a metric. Use narrowly scoped, explained exceptions when justified; discuss substantial redesigns or broad rule changes with the user.
- Add consistent docstrings to new functions and classes, following existing Continuum style. Document all parameters except `self`/`cls` in `Args`; omit that section when there are no parameters to document. Include `Returns` with the type and meaning when a function returns a meaningful value; omit it for functions with no result. Include `Raises` for intentional validation or operational exceptions relevant to callers. Class docstrings explain purpose; document constructor parameters where applicable. Keep imports at module scope.
- When modifying existing functions, clarify useful documentation for input contracts, modeling assumptions and failure behavior as part of that work. Leave unrelated functions alone; do not start a blanket docstring pass.
- Treat docstring-only corrections as documentation work: verify their signature/return coverage and that executable statements are unchanged. Keep broad formatting or lint refactors in the separately requested cleanup rather than mixing them into an ongoing documentation review.
- Inspect the resulting diff and run relevant regressions after lint fixes. Report checks performed, unresolved findings and justified exceptions. If tooling cannot run, state that explicitly rather than claiming the checks passed.
- During subsequent development, investigate new lint findings that may indicate incorrect behavior and concrete test failures promptly. Assess style and complexity suggestions pragmatically. The reviewed findings in the OpenDC cleanup report are an accepted demo baseline, not a separate cleanup milestone or a requirement to reach 10/10.
- Limit routine cleanup to task-owned changes. Broader branch cleanup is a separate reviewable change when requested; do not reformat unrelated files or overwrite the user's in-progress edits. Respect any instruction to leave work unstaged or uncommitted.
