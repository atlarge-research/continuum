# Offline measured replay

The demonstration explains how a compute-side digital twin observes a cellular-connected service, forecasts arrivals, evaluates capacity options and steers worker admission. It replays completed physical evidence and performs no experiment, forecast fit, simulation or control action. The initial capture uses KPN 5G trace emulation. The 6G context is service orchestration and future integration with partner network twins and DevOps platforms; the capture does not measure 6G radio behavior.

## Presentation and time

Overview pairs the physical system with its digital twin. Analysis pairs issued forecast history with per-scenario deadline predictions for the capacity alternatives and worker CPU requests on one screen. A shared scenario selection connects these views; a short interpretation dialog explains their meaning. Policy comparison explains decision capabilities beside completed-study results. Its diagrams explain conceptual policy logic: the reactive heuristic and twin both use physical feedback, while the twin adds forecasts and simulated alternatives before selecting an action. The adjacent graphs retain the recorded workload results. The light blue interface uses one standalone HTML that embeds scripts, CSS, SVG, official logos and compact evidence, using system fonts and direct disk opening. The physical/virtual separation and paired comparisons draw inspiration from [openDT's architecture](https://github.com/atlarge-research/opendt/blob/master/site/docs/concepts/architecture.md) and [comparison visualizations](https://github.com/atlarge-research/opendt/blob/master/services/grafana/provisioning/dashboards/power_dashboard.json), without requiring its runtime.

The playback strip keeps controls, time acceleration, shortcuts and bookmarks together, leaving more height for the Overview panels. Every playback view uses one authoritative cursor. Actual evidence appears only when its availability is established; forecasts may extend beyond the cursor after publication. Analysis follows the same issued-history rule in Latest mode. It can retain a selected already published operating forecast while its actuals mature: history before that publication remains visible, followed by that forecast through its original horizon. Later forecasts do not replace the pinned prediction. Reverse seeking excludes future publications. The completed-study comparison is explicitly independent of playback time and must not be confused with a simulated policy switch at the cursor.

The visible replay starts during operation with a ready forecast. Earlier observations initialize backlog and causal history internally. Controller proposal timestamps conservatively bound publication of forecasts and alternatives because exact issue times are unavailable. Resource publication uses a proved next serialized collection or a verified immutable-prefix boundary. Unsupported timing remains unavailable. Recorded scores retain the historical controller's assumptions rather than being recomputed by current software.

## Resources and service

Worker CPU and RAM bands show assigned application requests on full configured VM-capacity scales. Requests are grouped in a stable order by startup, finishing and processing, with proportional widths that support different-sized and fractional requests. They do not map CPU affinity or physical memory placement. The hatched CPU section denotes configured capacity outside the application's recorded admission budget; it does not establish measured Kubernetes or host-system use. System RAM reservations are not inferred. Reservations persist until physical release; finishing is distinct from completed application processing. The application CPU capacity counter sums the recorded admission budgets of accepting workers, excluding capacity outside the application budget. It is not free CPU or measured utilization. Reserves remain powered, and scaling changes admission rather than establishing a power-off saving.

A blue marker on each band describes available application samples separately from its request segments. Capacity ticks use configured CPU cores and GiB; exact request and measured values remain in hover details. CPU is a short-window rate normalized against configured VM cores; RAM is working-set memory normalized against configured VM memory. They are separate from application reservations and whole-node utilization. Partial coverage is visibly distinct and cannot stand in for a complete worker total. Recent per-Job measurements can cover different windows, so their aggregate can exceed nominal CPU capacity; the hover value remains accurate while only the marker position is capped. Small measured RAM use is not enlarged for visual effect. Missing values remain missing, including ready workers without assigned Jobs or application samples. Those empty ready workers display “Measured” as their monitoring-status label; this does not introduce zero-valued application samples or whole-VM utilization. “Partial” and “Missing” continue to describe sample coverage for assigned Jobs.

Worker cards retain the last complete, already-published update during short collection gaps, with an age label and the original observation time in hover details. Retention is bounded to three observation-gap allowances from dataset metadata and stops immediately on an explicit observer failure. The entire card is frozen coherently, including membership, admission and available samples; absent samples are not filled. Seeking derives this state directly from evidence in either direction. Counters, histories, forecast quality and decision interpretation retain strict observation coverage, so presentation continuity does not revise the evidence.

The deadline indicator uses the report's evaluated arrival cohort and terminal Kubernetes Job completion, measured from original API creation. It waits for published terminal evidence before confirming on-time completion. Classifier execution finish remains a separate diagnostic because cleanup and terminal reporting can add time. Failed outcomes count as missed; outcomes not yet confirmed remain pending. The provisional percentage divides on-time confirmations by all confirmed outcomes and explicitly excludes pending Jobs. The service target applies to the full evaluation cohort, which is shown in the completed-study comparison. The progress counter includes terminal completions outside the evaluated service cohort as well.

## Prediction and comparison

Forecast and physical history visuals share publication-gated recorded arrival counts. Overview uses fixed-origin intervals; Analysis aligns its arrival intervals to the selected forecast and aggregates native expected counts to those same intervals before calculating average absolute error. Partial groups, intervals crossing the visible operating start and intervals without full coverage are excluded from the error. Selecting a simulation scenario highlights its arrival pattern and drives the corresponding worker predictions without changing the action recorded by the controller. Solid bars show arrivals observed by the cursor; hatching marks the current interval while it fills. An interval ending does not prove a complete arrival census: a later first observation can still update a recent bin. Short non-atomic Job/Pod membership mismatches affect queue and placement completeness but do not by themselves establish lost arrival records, so they shade queue history rather than entire arrival bins. Expected counts and sampled futures are distinct. The shaded minimum-to-maximum range spans the captured sampled scenarios; a small scenario ensemble is not a calibrated confidence interval, and its range need not contain the expected forecast. Forecast error remains conservative and uses only elapsed bins with continuous full collection coverage, separately from the displayed recorded-arrival counts. Past portions of issued forecasts remain visible until the next ready publication, with genuine refresh discontinuities; new issues replace only future portions. Each historical segment begins at publication, retains its original bucket values and ends at the next ready publication, the cursor or its actual horizon. Display state is reconstructed from the published prefix in either playback direction. The latest ready forecast remains visible through skipped updates while its horizon still covers the cursor, with original issue age and an update status. The actual latest decision remains separate; retaining an old forecast never establishes a new simulated decision.

Analysis exposes every captured scenario’s deadline score for each capacity action against the service target. Coincident scores remain distinct, and the recorded choice considers the lowest scenario score. CPU allocation is the aggregate capacity committed over the recorded allocation window, in core-minutes; it does not become a per-scenario estimate when the display selection changes. The accompanying worker table compares instantaneous predicted application CPU requests with the sum of observed held CPU requests, separately from measured resource use. This shows how different demand futures can produce different service predictions even when the available workers remain saturated. Unavailable alternatives retain their captured reason, so reaching the worker limit is distinguished from missing evidence. Skipped forecast updates retain their recorded reasons in the replay. A recorded selection can be vetoed, delayed or superseded; unapplied alternatives remain hypothetical. Later physical outcomes describe the entire closed loop and cannot independently validate an unperformed alternative. Historical confirmation survives subsequent observation gaps while current freshness is reported separately.

Static control provides fixed, predictable capacity. Reactive control adapts to observed demand using configured rules. The forecast digital twin adds anticipation and explicit simulation of service/allocation choices, at the cost of model dependence and computation. Monitoring can support all three policies. The measured reactive arm is a custom worker-admission policy, not Kubernetes HPA or a universal industry baseline. Comparing forecast plus simulation with reactive control does not isolate simulation's incremental contribution; that requires a matched forecast-only ablation.

Measured comparisons require matched planned workloads, shared accounting and evaluation windows, accepted captures, and explicit initial-capacity differences. Service denominators retain failed and unfinished Jobs; completed-only latency is labelled accordingly. Allocation retains observation-coverage bounds, which are not statistical confidence intervals or energy/billing estimates. All available matched seeds remain selectable. Numerical findings and exact settings live with the evidence rather than this design account.

Final evidence replacement requires a completed-artifact handoff and renewed validation. Growing campaign artifacts are never polled. Node6 rendering establishes offline functionality; presentation-laptop and actual-monitor rehearsal establish usability in the intended environment.
